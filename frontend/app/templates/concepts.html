Key Concepts

Understanding the terminology used in DashVERSE dashboards helps you interpret the quality metrics and assessment results effectively.

Dimension

A high-level quality aspect of research software. Dimensions are the broadest category in the EVERSE quality framework and group related quality concerns together.

Examples Testing Documentation Licensing Version Control FAIRness

Indicator

A specific, measurable quality criterion within a dimension. Each indicator defines what aspect of quality is being measured and how it can be evaluated.

Examples Unit test coverage README exists License file present

Assessment

A complete quality evaluation of a software project performed at a specific point in time. It captures which software was assessed, when, and by what tools.

Contains Software info Date Multiple checks

Check

A single test result within an assessment. It represents the outcome of evaluating one indicator for a specific software project.

Status Pass, Fail, or NotApplicable
Tool Software that ran the check
Output Details and evidence

Schema

A formal data structure for quality assessment results. Schemas define the shape of the data, ensuring consistency and interoperability. Assessment data is generated using the assessment schema.

Examples Assessment Check Indicator

A Dimension contains many Indicators. An Assessment contains many Checks. Each Check evaluates exactly one Indicator.

Pass Rate

Most quality metrics on the dashboards (Software Pass Rate, Pass Rate by Dimension, Quality Score Heatmap, Compliance Heatmap) boil down to one number: the pass rate. It is computed entirely from the output and status fields on each Check in an assessment.

Step 1 — classify each check

DashVERSE normalises the raw output string and the status.@id of each check into one of four outcomes:

  • pass — output is one of true, valid, pass, Pass, passed
  • fail — output is one of false, invalid, fail, Fail, failed, or status.@id ends with FailedActionStatus
  • not_applicable — output is one of n/a, na, not_applicable, NotApplicable, NA, or error (errored checks are treated as skipped so a broken plugin doesn't drag the score down)
  • unknown — anything else; ignored by the pass-rate formula

Step 2 — aggregate

Pass rate is just the fraction of pass outcomes, counted over every check in the scope (per software, per dimension, per month, etc.): 

pass_rate = 100 × count(outcome = 'pass')
                  / count(*)

Result is a number between 0 and 100. Identical formula whether you're looking at one software's score for one dimension, the portfolio-wide pass rate, or a monthly trend — only the filter changes.

Worked example

Suppose an assessment of CFFinit reports five checks:

Indicator output Outcome
software_has_licensetruepass
software_has_citationvalidpass
software_has_testsfalsefail
software_has_documentationtruepass
archived_in_software_heritageerrornot_applicable

Three of the five outcomes are pass. The errored check counts as not_applicable and is excluded from the total. So: 

pass_rate = 100 × 3 / 5 = 60.0 %

Treating errored checks as not_applicable matches the EVERSE convention: a broken tool says nothing about the software's actual quality, so it shouldn't pull the score down.

Compliance threshold

A few views also report whether the pass rate is "compliant": pass_rate ≥ threshold. The threshold defaults to 75 % but is configurable per deployment via the app.compliance_threshold Postgres setting. Setting it to 0 disables thresholding (every score counts as compliant).

How to Read This Assessment

  • @context and @type: These fields are for JSON-LD (Linked Data), which makes the data machine-readable. They define the vocabulary and the type of object, respectively.
  • creator: Information about who performed the assessment.
  • assessedSoftware: Details about the software being assessed, including its name, version, and URL.
  • checks: This is an array of individual check results. Each check assesses a specific quality indicator (e.g., `license` or `citation`).
    • assessesIndicator: The unique identifier for the indicator being checked.
    • checkingSoftware: The tool that performed the check (e.g., `howfairis`).
    • status: The result of the check (e.g., `CompletedActionStatus` for Pass, `FailedActionStatus` for Fail).
    • output: A short, machine-readable output of the check (e.g., "true", "valid").
    • evidence: A human-readable description of the evidence found during the check.
